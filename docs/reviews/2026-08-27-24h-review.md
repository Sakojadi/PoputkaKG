## Verdict

This is careful work — the scheduler rework, the OOM-motivated singletons, the failure-counting
paths and the FSM payment guards are all better than the median for a solo-operator bot, and the
comments record *why* rather than *what*, which made this review much faster than it would
otherwise have been. Nothing in the 24 hours crashes the process or corrupts the campaign table,
and every `/admin/*` data or action route does carry `Depends(require_admin)` — I checked all 19
routes individually and found no missing-auth hole. What blocks a production deploy is not the new
code but what the new code now exposes: the admin panel must be internet-reachable for the xPay
callback to arrive, and `bot/config.py:26` ships a hardcoded default `SECRET_KEY` that, if the
Railway env var is unset, lets anyone forge an admin session and delete every user. Beyond that,
the two real gaps are that a single payment can mint two campaigns on a double-tap, and that the
new `payments` table is invisible to the admin panel while the admin panel's delete actions
orphan its rows — so money-in and service-out can no longer be reconciled by the operator. Two
further items deserve the operator's attention because they are self-inflicted by otherwise-good
changes: narrowing the OCR pool to two workers turned a bounded pileup into a permanent silent
outage of image moderation (I8), and an ordinary proxy error body from xPay reaches the user as
nothing at all rather than as an error (I7).

## Findings

### CRITICAL

#### C1. Hardcoded default `SECRET_KEY` (and admin password) — `bot/config.py:25-26`

```python
admin_password: str = "admin12345"
secret_key: str = "secret-super-key-poputka-admin-xyz-123"
```

**What's wrong.** The session cookie is signed (`itsdangerous`) with `config.secret_key`
(`app.py:41`). If `SECRET_KEY` is not present in the Railway environment, the app silently falls
back to a value that is committed to this repository. Signing key knowledge is total: an attacker
mints `{"admin_logged_in": true}`, signs it, and is logged in. Independently, `ADMIN_PASSWORD`
defaults to `admin12345` and — because a fresh deployment has no `admin_password_hash` row — the
plaintext fallback path at `app.py:204-207` accepts it.

**Why it matters now specifically.** Before the xPay work the panel could plausibly have hidden
behind an unadvertised URL. It cannot any more: `resolved_public_base_url` (`config.py:104-114`)
derives the callback origin from `RAILWAY_PUBLIC_DOMAIN`, meaning the same public hostname that
xPay posts to also serves `/admin`. The panel is now definitively internet-reachable.

**Failure scenario.** Someone finds the Railway hostname (they are enumerable, and the xPay
callback URL contains it). They request `/admin/login`, get a session cookie, observe it is
`itsdangerous`-signed, try the repo's default key, re-sign a forged payload, and land on
`/admin/users`. From there: `POST /admin/users/{id}/kick-from-group` deletes any user and all
their campaigns; `POST /admin/broadcast/users` messages every user of the bot from your bot;
`POST /admin/settings/general` sets the ad price to 0.01 and changes your admin password.

**How to fix.** Remove both defaults and fail closed at startup:

```python
secret_key: str            # no default
admin_password: str        # no default
```

Pydantic Settings will then refuse to construct `config` if the env vars are absent, which is the
correct behaviour for a credential. If you want a softer landing, keep the field but add a
validator that raises when the value equals the old default. Then rotate `SECRET_KEY` (which
invalidates existing sessions — fine) and set a real `ADMIN_PASSWORD`.

**Honest caveat.** I cannot see the Railway environment. If `SECRET_KEY` and `ADMIN_PASSWORD` are
already set there, this is *currently* not exploitable and drops to "remove the footgun before it
fires on the next environment". Please check before deploying — this one finding is the difference
between "ship it" and "do not ship it". Also note this default predates the 24-hour window; it is
reported here because the review explicitly asked for an admin-panel security assessment and
because these commits are what made the panel publicly reachable.

### IMPORTANT

#### I1. A double-tap on "Start" creates two campaigns for one payment — `bot/handlers/ad_flow.py:628-682`

**What's wrong.** `process_content_ok` reads the FSM data, inserts a `Campaign`, stamps
`payment.campaign_id`, schedules the job, and only clears the state at `:682` — after several
`await` round trips. aiogram 3 dispatches each update in its own task, so two callback queries from
two taps run concurrently. Both see `AdFlow.confirm_content`, both pass, both insert. There is no
guard on `payment.campaign_id` already being set (`:649-653` overwrites unconditionally).

**Why it matters.** The user paid for N publications once and receives 2N. The operator eats the
difference, and `price_paid` is written on both rows, so `spent_expr` in the dashboard
(`app.py:231-238`) double-counts the revenue too — the panel will tell the operator they earned
twice what actually arrived.

**Failure scenario.** A user on a slow mobile connection taps "✅ Всё верно" twice because nothing
visibly happened. Two campaigns, both active, both scheduled under *different* ids (`campaign_12`,
`campaign_13`), both posting to the group on the same interval. The group gets duplicate ads; the
user is delighted; the operator is out N publications and their revenue figure is wrong.

**How to fix.** Make the payment row the idempotency key — it is already unique per order:

```python
payment_db_id = data.get("payment_db_id")
async with AsyncSessionLocal() as session:
    if payment_db_id:
        payment = await session.get(Payment, payment_db_id)
        if payment is None or payment.campaign_id is not None:
            await callback.answer(...)   # already redeemed
            return
    ...
```

Better still, `await state.clear()` (or set a terminal state) *before* the DB work, so the second
task's state filter rejects it at the router. Belt and braces: a `UNIQUE` index on
`payments.campaign_id` would make the double-insert fail loudly rather than silently.

#### I2. The `payments` table is invisible to the admin panel, and admin deletes orphan it — `bot/web/app.py:531-581`, `:760-795`, `:798-813`

**What's wrong.** Three destructive routes — `admin_delete_campaign`, `kick_user_from_group`,
`delete_user_from_db` — remove `Campaign` and `User` rows. None of them touch `Payment`. There are
no foreign keys and no `ON DELETE` behaviour (`models.py:70-87` uses plain `Integer`/`BigInteger`
columns), so the rows survive with `user_id` and `campaign_id` pointing at nothing. And nothing in
the panel ever renders a `Payment`: `Payment` is imported in `app.py:20` solely for the webhook
lookup at `:131`.

**Why it matters — this is the Group A ↔ Group B seam, and it is the one that genuinely was not
reviewed.** The panel's revenue figures are derived entirely from `Campaign.price_paid`
(`app.py:231-238`). Money now enters the system through `payments`, and service is delivered
through `campaigns`. The only place those two are joined is `payment.campaign_id`, written at
`ad_flow.py:651`. Once a campaign is deleted that link is severed, and there is no UI that could
show it anyway. The operator has no way to answer "did this person actually pay?" or "which
payments came in with no campaign attached?"

**Failure scenario.** The documented known limitation is that a restart between `COMPLETED` and
content submission strands a paid user (`fsm.py:6-9`, `ad_flow.py:406-411` logs it and returns).
Say that happens. The user messages the operator: "I paid 500 som and nothing happened." The
operator opens the panel. `/admin/campaigns?q=<user_id>` → nothing. `/admin/users` → the user, zero
campaigns, zero spent. There is no `/admin/payments`. The only record that the money arrived is a
row in a table with no UI and a `WARNING` line in the Railway log. If the operator has since used
"kick from group" on anyone, that user's payment history is unreachable entirely.

**How to fix.** Two small pieces, in order of value:

1. Add a read-only `GET /admin/payments` listing `id`, `user_id`, `amount`, `status`,
   `campaign_id`, `created_at`/`updated_at`, filterable by status, with `COMPLETED` +
   `campaign_id IS NULL` as a first-class filter — that query *is* the "paid but undelivered" list,
   and it is the thing the operator will actually need.
2. In the three delete routes, either delete the matching `Payment` rows in the same transaction,
   or (better for an audit trail) leave them and null out `campaign_id` so orphans are explicit.
   Do not silently leave dangling ids.

#### I3. `aiohttp.ClientSession()` constructed per moderation call — `bot/services/moderation.py:347`

**What's wrong.** `moderate_image_openai` opens a fresh `aiohttp.ClientSession` for every call.
This is precisely the pattern that `bot/services/tg.py:1-6` and `bot/services/xpay.py:1-7` were
rewritten to eliminate: constructing a client builds a fresh SSL context and loads the full
certifi CA bundle, and the GC does not return that to the OS promptly.

**Why it matters.** Given the OOM history — `railway.toml` sets `MALLOC_ARENA_MAX=2` and an
uncapped restart policy specifically because of this — this is the last remaining instance of the
exact allocation the OOM fix was written to remove, and it is on the hot path: every ad submission
with a photo goes through `moderate_full_content` → `moderate_image_openai` (`moderation.py:384`).
It is also the source of the `Unclosed client session` noise in the test run.

**Failure scenario.** A burst of ad submissions (a promotion, a group of users at once). Each one
allocates an SSL context; each also base64-encodes the full image into a JSON body
(`moderation.py:331-341`), so a 5 MB photo becomes ~6.7 MB of string on top. RSS climbs, Railway
OOM-kills, `restartPolicyType = "always"` bounces the process, and — because FSM storage is
in-memory (`fsm.py:6-9`) — every user mid-flow, including anyone who has paid but not yet submitted
content, is stranded (see I2).

**How to fix.** Mirror `xpay.get_client()`:

```python
_session: aiohttp.ClientSession | None = None

def get_moderation_session() -> aiohttp.ClientSession:
    global _session
    if _session is None:
        _session = aiohttp.ClientSession(timeout=aiohttp.ClientTimeout(total=15.0))
    return _session
```

and close it from `bot/main.py`'s `finally` block alongside `close_xpay_client()` / `close_bot()`.
That also fixes the test-teardown warning.

#### I4. No rate limiting on either public entry point — `bot/web/app.py:107-146`, `:193-218`

**What's wrong.** Two unauthenticated endpoints accept unlimited requests.

- `xpay_webhook`: every POST with a body opens an `AsyncSessionLocal` and runs a `SELECT`
  (`:129-135`). If the transaction id resolves, `confirm_payment` (`ad_flow.py:429`) opens two more
  sessions and makes an outbound HTTPS call to xPay.
- `login_action`: unlimited password attempts, no lockout, no delay.

**Why it matters.** The webhook is *correctly* public and its trust model is sound — the body is
only a trigger and the xPay status endpoint is the sole authority (`:109-117`, `xpay.py:206-211`).
The gap is volume, not trust. And the login endpoint has no brute-force protection at all, which
compounds C1: if the panel is running on the default `admin12345`, an attacker does not even need
the signing key.

**Failure scenario.** Someone scripts 200 req/s at `/api/payment/xpay/webhook` with a body of
`{"qr_transaction_id": "x"}`. Each request is a DB round trip on the same event loop that runs
`dp.start_polling()` — bot responsiveness degrades along with the panel. If they have observed a
real transaction id (it appears in the QR flow), each request additionally becomes an outbound
xPay call, which may trip your merchant rate limits.

**How to fix.** For a solo-operator bot, keep it cheap: an in-memory sliding window keyed on client
IP, ~10/min on the webhook and ~5/min on `/admin/login`, returning 429. A `dict[str, deque]` with
periodic pruning is enough — but bound it (see M7). `slowapi` is the off-the-shelf option if you'd
rather not hand-roll.

#### I5. Session cookie has no `Secure` flag — `bot/web/app.py:39-43`

**What's wrong.** `SessionMiddleware` is added with only `secret_key` and `max_age`. Starlette's
defaults are `https_only=False` and `same_site="lax"`. The `lax` default is what saves you on CSRF
(good), but `https_only=False` means the cookie has no `Secure` attribute and will be sent over
plain HTTP.

**Why it matters.** A 7-day admin session cookie (`max_age=3600 * 24 * 7`) is a long-lived
credential. Any request that reaches the origin over `http://` — a typed URL, an old bookmark, a
link in a message, a captive-portal redirect — puts it on the wire in clear text.

**Failure scenario.** The operator opens the panel from café Wi-Fi, having typed the hostname
without `https://`. The browser tries `http://` first; the cookie rides along before the redirect.
Anyone on that network now has a week of admin access.

**How to fix.** One line:

```python
app.add_middleware(
    SessionMiddleware,
    secret_key=config.secret_key,
    max_age=3600 * 24 * 7,
    https_only=True,
    same_site="lax",   # explicit, so the CSRF mitigation is intentional rather than inherited
)
```

Note `https_only=True` will break local `http://localhost` development; gate it on
`config.resolved_public_base_url` being set, or on an explicit env flag.

#### I6. "Kick from group" deletes the user row but does not ban them — `bot/web/app.py:760-795`

**What's wrong.** The route bans-then-unbans in Telegram (removing them from the group), then
deletes all their campaigns and the `User` row itself. It never sets `is_banned = True` — and it
cannot, because it deletes the row that would carry the flag.

**Why it matters.** `get_user_lang` / `cmd_start` recreate a `User` row on the next `/start`
(`bot/handlers/start.py:49-55`), with `is_banned` at its `False` default (`models.py:23`). So the
`BanMiddleware` will not stop them. The operator will reasonably believe this button removes a
problem user permanently; it removes them for as long as it takes to press `/start`.

**Failure scenario.** A user spams the group. The operator hits "Исключить из группы". Their paid
campaigns are deleted (irreversibly, and with the payment rows orphaned per I2), they are removed
from the Telegram group, and thirty seconds later they `/start` the bot again as a brand-new user
and buy another placement. The operator has destroyed their own records and achieved nothing
durable.

**How to fix.** Decide what the button means and make it do that. If it means "remove and keep
out": keep the `User` row, set `is_banned = True`, deactivate campaigns rather than deleting them,
and kick from the group. If it genuinely means "forget this person": maintain a separate
`banned_user_ids` table that `BanMiddleware` consults, so the ban outlives the row. Also add a
confirmation showing what is about to be destroyed (N campaigns, M som of payments) — right now the
most destructive action in the panel is a single unguarded POST.

#### I7. `_unwrap` raises `AttributeError`, not `XPayError`, on a non-dict JSON body — `bot/services/xpay.py:60-74`

**What's wrong.** `body = resp.json()` is guarded only against *unparseable* JSON (`ValueError`). If
the body parses successfully but is not a dict — a bare string, a list — then line 68's
`body.get("status")` (or line 69's `body.get("message")`, reached first when the status code is not
200 and the `or` short-circuits) raises `AttributeError`. Verified:

```
>>> _unwrap('/p', resp_with_status_429_and_body_"Too Many Requests")
RAISED: AttributeError 'str' object has no attribute 'get'
```

**Why it matters.** Every caller — `create_payment`, `get_payment_status`, and through them
`process_payment` (`ad_flow.py:487-492`) and `confirm_payment` (`ad_flow.py:447-451`) — catches
`XPayError` only. An `AttributeError` sails straight past those handlers and out of the aiogram
handler entirely, so the intended `payment_not_found` alert never fires.

**Failure scenario.** xPay sits behind a CDN or WAF. It rate-limits or 502s and returns
`"Too Many Requests"` or `["error"]` with `Content-Type: application/json` — a very ordinary thing
for an edge proxy to do. The user presses "Оплатить" and *nothing happens at all*: no QR, no error
alert, no spinner resolution. They press it again, and again. Meanwhile the exception is buried in
the aiogram error log. This is strictly worse than the failure the code already handles gracefully.

**How to fix.** One guard, right after the parse:

```python
if not isinstance(body, dict):
    raise XPayError(f"xPay {path} returned a non-object body (HTTP {resp.status_code})")
```

#### I8. Two hung OCR threads permanently disable image moderation — `bot/services/moderation.py:288-323`

**What's wrong.** This is a regression introduced *by* the Group A OOM fix, which is why it is worth
flagging despite the fix itself being sound in intent. The comment at `:286-288` correctly notes
that `asyncio.wait_for` cancels the future but not the thread. With
`ThreadPoolExecutor(max_workers=2)`, two tesseract runs that hang past the 2-second timeout occupy
both workers **forever** — nothing can reclaim them. From that moment every subsequent
`moderate_image_ocr` call queues behind them, times out, is swallowed by the bare
`except Exception: pass` at `:321-322`, and returns `(True, "")` — "this image is fine".

**Why it matters.** OCR moderation silently switches off process-wide, permanently, with no log
above `debug` level. The previous `asyncio.to_thread` default (32 shared workers) made a hang a
bounded pileup; narrowing the pool to 2 converts it into a permanent outage. The memory reasoning
was right; the availability consequence was not considered.

**Failure scenario.** Two users upload malformed or pathological images that wedge tesseract (a
decompression-bomb-shaped PNG, a corrupt JPEG). Both workers are gone. Every image submitted from
then until the next restart passes OCR moderation unchecked — so text-in-image ads with phone
numbers, links, or adult content go straight to the group. Nobody notices, because the only signal
is a `debug` line. The OOM restart policy is what eventually clears it, which is a grim way to
depend on a crash.

**How to fix.** Pick one: (a) a `ProcessPoolExecutor`, whose workers can actually be killed on
timeout — the correct fix, and it also isolates tesseract crashes; (b) keep the thread pool but log
at `warning` when the executor queue is non-empty, so a wedge is visible; (c) raise `max_workers`
modestly and accept a bounded pileup. Do not leave it at 2 with a silent `pass`. At minimum,
change `except Exception: pass` at `:321` to log.

#### I9. Password salt and hash are written in two separate transactions — `bot/web/app.py:1019-1023`

**What's wrong.**

```python
salt = secrets.token_bytes(16)
password_hash = _hash_password(new_password.strip(), salt)
await set_setting("admin_password_salt", salt.hex())
await set_setting("admin_password_hash", password_hash)
```

`set_setting` (`settings_store.py:32-40`) opens and commits its own session, so these are two
independent transactions. If the process dies or the DB connection drops between them, the store
holds the **new salt paired with the old hash**.

**Why it matters.** `login_action` (`app.py:199-207`) checks `if stored_hash and stored_salt:` —
both are present, so it takes the hash path and never falls back to the plaintext `.env` password.
But `pbkdf2(any_password, new_salt)` can never equal the old hash. **No password works, and there
is no in-app reset.** Recovery means manually editing `app_settings` in the production database.

**Failure scenario.** The admin changes the password. Between the two commits, Railway OOM-kills the
process — which, per `railway.toml`, is the known failure mode of this app, and password changes
happen on the same event loop as everything else. It restarts, and the panel is now permanently
unreachable through its own login form.

**How to fix.** Write both keys in a single transaction. Note that reordering does **not** help —
"new hash + old salt" is just as broken as "new salt + old hash" — so a `set_settings_many(...)`
helper that commits once is the only correct fix:

```python
async def set_settings(pairs: dict[str, str]) -> None:
    async with AsyncSessionLocal() as session:
        for key, value in pairs.items():
            setting = await session.get(AppSetting, key)
            if setting is None:
                session.add(AppSetting(key=key, value=value))
            else:
                setting.value = value
        await session.commit()
    _cache.update(pairs)
```

Independently, consider storing salt and hash in one `AppSetting` value (`f"{salt}${hash}"`), which
makes the invariant unbreakable by construction.

### MINOR

#### M12. The webhook returns 200 on transient failures, so xPay never retries — `bot/web/app.py:143-146`

`xpay_webhook` wraps both the DB lookup and `confirm_payment` in `except Exception`, logs a warning,
and still answers `{"status": "ok"}`. Always-200 is deliberate and correct for *unknown or forged*
transaction ids (`:109-117` explains why). It is wrong for infrastructure failures: if the DB is
briefly unavailable, or `_get_auth` fails because xPay's own login endpoint is momentarily down,
we tell xPay we handled a callback we did not handle, and it will not redeliver. The payment stays
`WAITING` and the only fallback is the user's check button — which, per M13, may be unreachable.
Returning a 5xx for infrastructure failures while keeping 200 for unknown ids would let xPay's
retry mechanism do its job. Minor rather than Important because the check button covers the common
case and the window is small.

#### M13. `check_payment_cb` is state-gated, so the check button dies with the FSM — `bot/handlers/ad_flow.py:547`

`@router.callback_query(AdFlow.waiting_payment, F.data == "check_pay")` requires live FSM state,
but storage is in-memory (`fsm.py:6-9`) and restarts are routine under
`restartPolicyType = "always"`. After a restart the button matches no state-gated handler and falls
through to the bare `@router.callback_query()` fallback at `:829`, which *does* answer — the user
gets "⚠️ Сессия была обновлена… нажмите /start". So they are not left hanging silently, but the
message is misleading: it implies pressing `/start` fixes things, and it does not. Their money is
gone and `/start` begins a fresh unpaid order.

This is the bot-side face of **I2**: the user cannot self-recover, and the operator cannot see the
payment either. A stateless `F.data == "check_pay"` handler that looks up the caller's most recent
`COMPLETED` payment with `campaign_id IS NULL` and re-enters `AdFlow.content` would close the loop
from both ends, and would compose well with the `/admin/payments` page from I2.

#### M14. A commit failure after a successful send is charged to the user as a send failure — `bot/handlers/ad_flow.py:138-156`, `bot/services/group_posts.py:77-90`

`await session.commit()` sits inside the same `try` as the Telegram sends, and the handler treats
any exception as "the post failed": it re-fetches, increments `failure_count`, and does *not*
decrement `publications_left`. If the send succeeded and the *commit* is what raised (a dropped
Postgres connection), the ad is live in the group but uncounted — the user gets a free
publication, and the campaign accrues a spurious failure. Five such blips deactivate a campaign
that has been posting perfectly. Moving the commit outside the send `try` (or recording a
`sent_ok` flag before committing) would make the counter honest in both directions. Related to M10,
but this one has a plausible trigger rather than a race.

#### M15. Shutdown cleanup either never runs or runs too early — `bot/main.py:68-78`

`uvicorn.Server.serve()` installs its own signal handlers, while `dp.start_polling` is explicitly
told not to (`handle_signals=False`). On SIGTERM, `serve()` returns but the polling coroutine does
not, so `asyncio.gather` blocks and the `finally` — `close_xpay_client()`, `close_bot()` — never
executes; the process dies by SIGKILL. In the other direction, if `server.serve()` *raises* (port
already in use), `gather` propagates immediately without cancelling its sibling, so `close_bot()`
closes the aiohttp session out from under a still-running polling task, producing a burst of
tracebacks and "Task was destroyed but it is pending". Neither costs data — the singletons are
process-scoped and the OS reclaims them — which is why this is Minor. Fix with
`asyncio.wait(..., return_when=FIRST_COMPLETED)`, cancelling the loser before the cleanup block.

#### M16. Filter restore pushes a duplicate history entry — `bot/web/templates/base.html:1688-1695`

`restoreFiltersOnLoad` calls `navigateTo(path + '?' + stored, true)` — the `true` is `push`. On a
full page load of `/admin/campaigns` with stored filters, that pushes a *second* history entry for
what the user sees as the same page. Pressing Back returns to the bare URL, fires `popstate`, and
re-renders the unfiltered list; the user must press Back twice to leave, landing on an unfiltered
view in between. Use `navigateTo(..., false)` plus an explicit `history.replaceState`, which is
clearly the intent. Cosmetic, but it is the kind of thing the operator will hit every single day.

#### M1. Scheduler mutated before the DB commit — `app.py:504-507`, `:521-524`, `:743-753`; `ad_flow.py:697-699`, `:757-760`

`remove_campaign_job()` / `schedule_campaign()` are called before `session.commit()` in five
places. If the commit fails, the scheduler and the DB disagree: a "stopped" campaign is still
`is_active=True` in the DB with no job (it silently stops posting paid publications until the next
restart, where `sync_jobs_with_db` restores it), or a "resumed" campaign has a job while the DB
says inactive (the job then no-ops on every fire, forever). **This requires a commit failure, which
is not common** — hence Minor. The fix is free: commit first, then touch the scheduler. Worth doing
because `sync_jobs_with_db` already exists as the safety net, so the failure is self-healing on
restart and therefore easy to never notice.

#### M2. Bot `/admin` revenue and panel revenue disagree — `bot/handlers/admin.py:38-43` vs `bot/web/app.py:231-238`

`cmd_admin` now computes `sum(publications_total) * get_price_per_ad()` — the *current* price
applied retroactively to all history. The web dashboard uses `spent_expr`, which prefers the stored
`price_paid` and only falls back to the current price for legacy rows with `price_paid` 0/NULL. The
moment the price is changed in settings, the two figures diverge, and the bot's is the wrong one
(it re-prices past sales). Use `spent_expr` in both, or drop the revenue line from `cmd_admin`.

#### M3. Bot token in a redirect URL — `bot/web/app.py:160-171`

`get_telegram_photo` 302s the admin's browser to
`https://api.telegram.org/file/bot{config.bot_token}/{path}`. The token lands in browser history,
in the browser's URL bar, and in the `Referer` of any subsequent navigation from that URL. It is
admin-only and the admin owns the bot, so this is not an escalation — but a bot token is the single
credential that controls the whole bot, and there is no reason to widen its blast radius. Stream
the bytes through the app instead of redirecting (`bot.download_file` → `StreamingResponse`).

#### M4. Raw exception text interpolated into a redirect URL — `bot/web/app.py:906`

```python
msg = f"Ошибка+отправки:+{e}"
return RedirectResponse(url=f"/admin/broadcast?msg={msg}", status_code=302)
```

A Telegram API error containing `&`, `#`, `%`, or a newline truncates or corrupts the query string
— the operator sees a mangled or empty error message exactly when they most need the real one.
This is **not** XSS: Jinja autoescapes `msg` on render. Fix with
`urllib.parse.quote_plus(str(e)[:200])`. The other hand-built `msg=` URLs in this file use
pre-encoded literal `+` strings and are fine; only this one embeds untrusted text.

#### M5. Concurrent broadcasts are possible — `bot/web/app.py:951-978`

`broadcast_users` loads all users into a list and fires a single `_spawn`. Two submits (a
double-click, or an impatient retry after the redirect) run two full broadcasts concurrently:
every user is messaged twice, at double the send rate, with no way to see progress or cancel. A
module-level `_broadcast_running` flag rejecting the second submit would cost three lines. The
`select(User)`-into-a-list is unbounded memory too, though at this user count that is theoretical.

#### M6. Dead destructive route — `bot/web/app.py:798-813`

`POST /admin/users/{user_id}/delete` deletes a user and all their campaigns, but no template posts
to it (`users.html` links only `toggle-ban` and `kick-from-group`). Either wire it up or remove it
— an unreferenced destructive endpoint is attack surface with no compensating usefulness, and it
will drift out of sync with `kick_user_from_group`, which does almost the same thing.

#### M7. If you add the rate limiter from I4, bound it

Flagging pre-emptively given the OOM history: the natural implementation is a dict keyed on client
IP, which an attacker rotating source addresses grows without limit. Use a fixed-size structure
(e.g. `collections.OrderedDict` capped at a few thousand entries with LRU eviction), not a plain
`dict` you intend to prune "later".

#### M8. `init_db` swallows every migration failure silently — `bot/database/db.py:41-53`

The outer `except Exception:` retries without `IF NOT EXISTS`, and the inner one is a bare `pass`.
A migration that genuinely fails — say `ALTER TABLE payments ADD COLUMN campaign_id` on a Postgres
instance where `payments` does not yet exist in the expected shape — leaves no trace, and surfaces
much later as a confusing runtime error in `process_content_ok`. Log at `warning` in the inner
handler. Cost: one line; value: the difference between a five-minute and a two-hour diagnosis.

#### M9. `settings_store._cache` is correct only because there is exactly one process — `bot/services/settings_store.py:8-10`

The comment says so, which is good. Worth stating the consequence too: a second Railway replica
would serve two different ad prices, and `set_setting` from one would never reach the other. Not a
bug today (single process, `railway.toml` has one `startCommand`), but it is a constraint that will
not announce itself when violated.

#### M10. `post_ad` decrement is not atomic — `bot/handlers/ad_flow.py:125`

`campaign.publications_left -= 1` is read-modify-write. The scheduler cannot overlap a job with
itself (`max_instances: 1`, `scheduler.py:22`), so the only overlap window is the immediate
`_spawn(post_ad(...))` at `:659` racing a resume-triggered job. **This requires an implausibly
precise sequence** and I could not construct a realistic trigger — recording it only for
completeness. If you ever raise `max_instances`, this becomes real; a
`UPDATE ... SET publications_left = publications_left - 1 WHERE publications_left > 0` would make
it safe.

#### M11. Long outages shift, but do not lose, publications — `bot/services/scheduler.py:20-24`

`coalesce: True` with `misfire_grace_time: 300` means an outage longer than 5 minutes collapses all
missed runs into one. `publications_left` is not decremented for the missed runs, so nothing is
lost — the schedule just slides later. This is the right trade (the alternative is a burst of N
posts at once when the process comes back), but the operator should know that repost *timing*
drifts across restarts, because a customer may notice.
